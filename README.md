# 库存补货与发货建议

根据运营销售预测、FBA可用库存、货件到仓日期和本地库存，逐日模拟库存与未满足需求，生成快递、空运、海运建议量，再计算本站本地库存实际能发出的数量。

结果用于安排补货、识别到货前的断货风险、核对货源不足和异常在途。它是决策建议；跨站点借调、同SKU货源核销、实际物流可行性仍需业务确认。

本说明对应 **2026年11月19日的最新修正版源码**。GitHub `main` 保留首次修正前的原始代码，本次文档和最新源码放在独立分支。原始备份提交为 `a50d135927f0b7a2b4011e39e087dce1b42a5d5f`，标签为 `original-before-day0-fix-20261113`。查看文件时应确认当前所在分支，不能用 `main` 的旧代码推断本说明中的最新行为。

## 先看结果时怎么用

1. 先核对业务日期、站点、MSKU、积加SKU、发货定位和预测口径。原始定位为“不发货”的行先人工排除。
2. 在“预估”表查看首次断货前可售天数、断货时间与损失销量，判断是否存在来不及补的风险。
3. 看 `dhl_pre`、`air_pre`、`sea_pre`，分别是快递、空运、海运建议量。
4. 下发前看对应的“实际可发货数”和“缺货数”。建议量不等于已有货源能发出的量。
5. 同一积加SKU可能对应多个MSKU或店铺；按SKU汇总核销本地货源，再确认最终发货单。
6. 需要借调、存在接收差异、逾期货件或查验货件时，结合异常明细核对。比较表用于复核预测，不能直接将两种口径的建议量相加。

## 计算原理

### 第0天与每日可用库存

模拟起始日就是第0天。模拟N天时覆盖第0天至第N−1天；例如11月16日起模拟3天，是11月16、17、18日。

每天先把当天全部到货加入库存，再消耗当天需求。到货当天即可参与销售；同日多笔到货先合计。

```text
当日可用 = 昨日结余 + 当日到货
当日损失销量 = max(当日需求 - 当日可用, 0)
当日结余 = max(当日可用 - 当日需求, 0)
```

当日需求3、可用2.4，则只损失0.6，不是损失整天的3。恰好售罄没有未满足需求，不算断货。浮点计算中接近0的差额按容差处理，避免0.1等小数造成虚假断货。

损失销量是预测的未满足需求，可以有小数；程序不把已损失需求作为欠单累积到下一天。到货后恢复销售，也不会自动追回此前损失。

### 需求曲线和模拟长度

基础版按真实自然月计算：

```text
MSKU日均 = Listing月度预估销量 / 该自然月天数 × 款式销占比 × SKU销占比
```

当月从起始日计算到月底，包含起始日；后续月份按各月真实天数展开。月份排序后，最多取目标天数。每行“总发货天数”优先，缺省短尾/中尾120天、长尾/迭代105天。

如果预测月份不够，程序不会自动补足目标天数。应确保预测覆盖整个计划周期，否则结果只覆盖实际生成的需求列表。

3.0支持运营提供 `日均1/天数1`、`日均2/天数2` 等配对列：按数字顺序拼接Listing日均，再乘款式销占比与SKU销占比，覆盖模拟开始的前若干天。前段结束后回到**对应自然日期**的月度预测，不从首月重新开始，也不延长原模拟长度。

`天数=0~30` 表示30天；`30~45` 表示15天。区间文本仅用于计算长度，所有分段连续拼接，不按区间起点留空。相同站点+Listing的各月行应保持分段参数一致，因为当前分组取各列首个非空值。

### 三个渠道覆盖什么缺口

程序读取销占比表中的 `快递`、`空运`、`海运` 三个整数阈值。空值分别默认5、20、60。它们表示从第0天起的到货偏移天数，应按顺序配置；主程序不会把展示用的“在途天数”和“打包时间”重新相加替代这些阈值。

以快递6、空运25、海运40为例：

| 时间范围 | 归属 |
|---|---|
| 第0至第5天，即`[0,6)` | 本次最快发货也赶不上的损失；计入总损失，不计入三渠道建议 |
| 第6至第24天，即`[6,25)` | 快递建议覆盖 |
| 第25至第39天，即`[25,40)` | 空运建议覆盖 |
| 第40天至预测最后一天，即`[40,N)` | 海运建议覆盖 |

空运到货当天归空运，海运到货当天归海运；边界没有重复计算。同样的阈值不代表物流成本最优方案，程序按固定覆盖窗口计算。

### 向上取整与余量结转

先汇总各窗口的**实际每日缺口**，再按快递→空运→海运处理。前一个渠道向上取整多出的库存，会保留并抵扣后续窗口。

当前两套工具中的核心计算相同：

```python
surplus = 0.0
for window in windows:                  # 快递、空运、海运的每日缺口列表
    shortage = sum(window)
    quantity = math.ceil(max(0, round(shortage - surplus, 10)))
    suggestions.append(quantity)
    surplus += quantity - shortage      # 内部余量保留原精度
```

例如三个窗口分别缺0.2、0.2、0.3件：快递发1件，多出的0.8依次覆盖后面缺口，最终建议为 **1、0、0**，合计1，而不是三个窗口各发1件。没有额外发货限制且阈值正常时，三建议总量相当于对“快递到货日及以后可补缺口”整体向上取整；临近整数时以代码中的小数精度处理为准。

因此，**断货总损失1点多而建议合计1并不一定少发**。举例：总损失1.259235，其中快递到货前损失0.347532，可补缺口只有0.911703，向上取整为1。不能直接对全周期损失1.259235取整得到2，再要求本次发货追回已经赶不上的损失。

### 可售天数与断货日期为什么可能不一致

| 字段 | 当前计算口径 | 使用时注意 |
|---|---|---|
| FBA在库可售天数 | 初始FBA库存可覆盖的完整需求天数，最多使用165天需求 | 3.0初始库存可能含已计入的接收差异 |
| FBA总可售天数 | 初始库存加全部在途，视为起始时立即可用，最多使用135天需求 | 没有体现货件实际到货前的空档 |
| 总库存可售天数 | 再加本地锁仓数，最多使用165天需求 | 不等于本地货已经能当天到FBA |
| 本地库存可售天数 | 总库存可售天数−FBA总可售天数 | 两项上限不同，不能当成本地库存独立除日均 |
| 预估在库日均 | FBA库存÷FBA在库可售天数，再保留两位小数 | 是倒算指标，不是直接输出原始预测日均 |
| 首次断货前可售天数 | 逐日模拟中首次发生未满足需求前的完整天数 | 判断连续不断货时更有参考价值 |
| 断货风险总天数和断货总损失销量 | 逐日模拟的缺货日期数及当日未满足需求合计 | 不等于本地货源不足，也不等于建议总量 |

静态天数用于看库存总量大致能覆盖多久。判断“是否会在到货前断货”应看实际日期模拟。最终合并表当前只展示前三段断货明细，不能一概用三段之和代替所有断货的总计。

最终展示另有强制归零规则：FBA库存为0时在库天数归0；再且已出运为0时FBA总可售天数归0；再且本地锁仓为0时总库存可售天数归0。这些条件没有检查FBA预占或提货中，因此存在这些货件时，展示天数仍可能被覆盖为0。

### 建议量、实际可发和缺货数

实际货源分配当前只使用**目标站点对应的本地仓库存列**，按快递→空运→海运依次扣减：

```text
建议量 = 实际可发货数 + 本地货源缺货数
```

例如海运建议36件，CA本地只有6件，则实际可发6、海运缺货30。US本地有库存时可能提示“借调=是”，但不会自动跨站点调拨，也不保证其他站点足够借满。

当前逐行重新初始化本地库存，同一SKU在多个MSKU/店铺间没有全局扣减。因此不能不经汇总就将所有“实际可发货数”直接下发。共享库存、海外仓库存、已下单、已生产未发、本地在途等主要作为辅助信息展示，不会自动补齐本轮本站本地货源。

## 在途异常和接收差异

### 3.0如何得到预计到仓日期

`inbound_process.py` 将发货单及明细与物流追踪关联。追踪FBA ID清洗后截取前12位作为键；重复记录会留痕，并按原始“入库时间”排序取首条，不是把多行最新节点自动拼成一条。

预计出运日期优先追踪表入库时间，缺失时用发货单提货日期。对“入库→离港”“离港→到港”“到港→签收”三段，能解析两个端点时采用节点间天数，否则用国家、物流商、物流渠道、地区匹配的标准时效补齐。最终ETA为出运日加三段天数。

缺US地区映射或标准时效参数时，会输出问题记录并报错；先修参数再重跑。当前解析函数仍可能把含“预计”的日期文本解析为节点日期，不能把所有已解析值都视为已发生的实际节点。

### 预计到仓日期早于运行日

当前规则是对早于业务运行日的ETA **只加7天一次**，并输出原日期、加7后日期及“是否计入在途”标记，不循环加到未来。

假设运行日11月16日：11月13日→11月20日标“是”；11月9日→11月16日标“是”；11月8日→11月15日标“否”。

注意当前实现：标“否”的记录仍保留在“在途货件-正常”中，没有按该标记删除。逐日模拟只会在对应到货日期入库，所以仍在起始日前的货件不会入库；但静态在途汇总仍可能包含它，导致静态天数和断货模拟口径不一致。遇到这种记录应确认真实物流进度，修正源数据/到仓日期后重跑，不能仅凭标记认定已经从全部库存口径剔除。

新版此规则只处理发货单普通在途；接收中货件先被分开，未出库预占后来追加，不经过该步骤。基础版旧Notebook则先合并普通在途、预占和历史待发，再处理逾期，作用范围不同。

### 不计入在途的查验货件

查验登记按FBA ID匹配：

- “是否纳入库存计算=否”：从普通在途剔除，并输出查验详情和MSKU汇总。主表“不计入在途的查验量”用于追踪这批货，不能再手工加回可用库存。
- “是”：用“纳入库存计算后签收日期”覆盖普通在途ETA；日期为空或无效时报错。覆盖后如仍早于运行日，仍会进入加7天规则。

新版处理顺序是先分出接收中，再处理查验，最后追加预占；查验规则不会自动覆盖所有来源。缺查验登记文件时当前新版脚本会跳过，运行人员应确认确实没有待管控查验货，而不是把漏文件当成已排除。

### 接收中货件的差异量

```text
已收量 = 发货量 - 差异量
接收天数 = 运行日 - 实际到仓日期
是否已计入可售 = 是，当接收天数 <= 7 且差异量 > 0
```

预处理脚本先打标；3.0主程序再把“是”的差异量按店铺+SKU+MSKU加到初始FBA可用库存，并输出 `差异量-已计入可用库存`。这是本程序的模拟假设，不表示平台事实已经全部转为可售。

“预估”主表的 `差异量` 来自标“否”的接收汇总；`差异量-已计入可用库存` 是已经加入本轮初始库存的部分。两列口径不同，不能重复相加。

发货100件、差异20件、接收7天：已收80，差异20计入3.0初始库存；接收8天则不加。差异负数保留，不取绝对值；例如差异−5会得到已收105且不加差异。当前缺到仓日期按0天、未来日期可能为负天数，也可能满足“是”，需人工核对这类记录。

### JP适配

从JP本地已出库调拨数据匹配实际出库日期，转换为普通在途字段：状态固定“已出运”、ShipmentId用固定占位值，仓库由平台站点去掉`AMAZON:`后加`_FBA`。

物流方式**精确等于“空运”**时ETA为实际出库+15天，其他任何值为+25天，不查新版三段标准时效表。随后追加并替换E盘新版文件的“在途货件-正常”sheet，其他sheet保留。

当前没有与已有FBA/调拨在途去重，没有正量/状态/JP站点的额外过滤，也没有逾期加7处理。**重复运行追加会重复计数**；需要重跑时应先重新生成干净的新版基础在途，再追加一次，并核对源表调拨单号是否重复。

## 最终结果的比较表

“预估”用于运营预估主方案；“预估VS15”“预估VS30”“预估VS60”并列比较运营口径与近期销量参数生成的方案。后缀 `_15/_30/_60` 是对应比较口径，不是同一主方案额外追加的发货量。

当前合并使用店铺-站点+MSKU键，比较表要求一对一匹配。`在库天数差=运营在库天数−近期口径在库天数`；`在库日均比=运营预估在库日均÷近期口径预估在库日均`。分母为0可能出现无穷值，不能机械用该比值决定发货。7/15/30天日均展示列也不等于本次主方案已经切换为这些日均。

## 当前已知限制和核对事项

- “发货定位=不发货”没有清零建议/实际量，补货标识的销占比条件还存在优先级问题，可能错误覆盖标识。应以原始定位先排除，再核对数量；本次文档发布未修改此逻辑。
- 同SKU本地库存没有跨行统一扣减，不能把逐行实际量当作最终全局配货单。
- `FBA在途`展示按“已出运+FBA预占”重算，没有提货中；逐日到货模拟却使用正常在途sheet中全部状态。展示量和模拟量的范围可能不同。
- 逾期标“否”没有从正常sheet删除；JP追加没有去重；缺到仓日的接收差异可能被加库存。详见上述对应规则。
- 基础版在途注释中的出运日期回填与实际表达式存在差异，不能依赖注释理解成完整三级回填。
- 新版在途没有逾期记录时，异常详情/汇总变量可能未初始化；无接收记录时，空汇总可能缺“是否已计入可售”列，导致下游筛选失败。这些场景尚需后续修复。
- 3.0主表合并部分接收/查验汇总没有像比较表一样校验MSKU键唯一，键重复可能放大行数。运行后应比较行数并核对重复店铺+MSKU。
- 路径仍混合E盘固定路径、脚本所在根目录和D盘固定JP路径；将副本移入其他目录不会自动迁移业务数据。新版在途普通输出和E盘“新版”输出同时存在，JP只改E盘新版文件。
- 预测月份不足会缩短模拟期，所有库存天数还受各自需求列表上限影响。

本仓库保留业务数据在本地，不上传库存、发货单、Hyper和结果Excel。本次同步的Notebook副本清除了执行输出，避免把历史业务结果当作源码内容；原本地业务文件不因此改变。

## 验证和维护

现有函数回归测试可从 `code` 目录执行：

```powershell
python -m pytest test_shipping_recommendations.py test_month_sales_utils.py -q
python test_month_sales_utils.py
```

测试覆盖日期、自然月、实际缺口、到货当天、渠道边界、前缀预测和取整余量等函数行为。它不代表所有真实业务输入已通过端到端验证，也不替代业务对库存来源、货件状态、借调和发货定位的确认。

本次发布前在Python 3.11.1、pandas 2.2.3、pytest 8.4.2环境执行上述两条命令：68项pytest用例通过，月份汇总脚本输出`ok`。有6条pandas未来版本兼容提示，未改变本次结果。本次未重跑整批真实业务数据。

修改计算规则时，应同步两套工具和对应测试，并使用同一业务日输入比较前后结果。保留每次运行的程序版本、输入快照、参数、异常明细和最终文件，才能解释某个MSKU为什么增发、减发或没有建议。
